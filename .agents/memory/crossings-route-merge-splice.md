name: Crossings route merge-splice corruption
description: me/crossings.ts has been merge-corrupted repeatedly; symptoms and the shared CrossingsRow guard
---
The personal and blended crossings handlers in `artifacts/api-server/src/routes/me/crossings.ts` are near-twins, and merges have repeatedly spliced one handler's cutoff variable names (`spinCutoff`/`blendedWeekCutoff`) or block tails into the other — including a committed syntax error (misplaced `export default router;` mid-function).

**Why:** twin code blocks confuse 3-way merge; a splice compiles as ReferenceError-at-runtime (503 → empty dial) or a TS syntax error.
**How to apply:** a registered `typecheck` validation step (`pnpm run typecheck` — builds libs then typechecks every artifact) now gates this; run it after any merge. It happened a THIRD time (splice landed at HEAD even in the commit whose message claimed to repair it) — always verify the working file, not the commit message. The known-good reference is the pre-merge personal handler (own `cutoff`/`weekCutoff`/`monthCutoff`, `CrossingsRow[]` items, no topArtistNames) plus the blended handler's own `spinCutoff`/`blended*` names. Also eyeball the "Windowed predicates" sections of BOTH handlers. `CrossingsRow` is now a single shared type exported from lib/db (used by both the route and the `crossings_cache.data` $type) — keep it that way.

**Update (Aug 2026):** a dedicated smoke test (`artifacts/api-server/test/me-crossings-smoke.test.ts`) now boots the app and hits both crossings endpoints, failing CI on this corruption class even when typecheck passes.

**Update (2026-08-05):** splice #3 landed the same way (blended handler's spinCutoff/blendedWeekCutoff names + duplicated handler tail spliced into the personal handler). Typecheck alone didn't gate it. A `server-tests` validation step now runs the api-server vitest suite excluding `**/*-db.test.ts` (~30s, includes me-crossings-smoke.test.ts which boots the real app and fails on any 5xx from either crossings handler).

**Blended L2 (Aug 2026):** the blended route now also has a Postgres L2 (`blended_crossings_cache`, single row id=1, boot-migrated) mirroring the per-user `crossings_cache` pattern; tests that expect a fresh compute must clear BOTH L1 (`_testOnly_clearBlendedCrossingsCache`) and L2 (`_testOnly_clearBlendedCrossingsL2Cache`, which awaits any in-flight fire-and-forget write). Fire-and-forget L2 writes (personal AND blended) are tracked as in-flight promises so cache busts order the delete after any pending write — otherwise a slow write lands after the bust and resurrects stale data (manifested as wrong counts under parallel test DB load). Splice #5 swapped a HELPER CALL across handlers (personal handler calling `readBlendedL2Cache()` instead of `readL2Cache(user.id)`) — typechecks fine, and only fails when the global blended L2 row happens to be populated (e.g. another test file's request), so it looks like parallel-run flakiness. After any merge, grep that the personal handler reads `readL2Cache(user.id)` and blended reads `readBlendedL2Cache()`.
